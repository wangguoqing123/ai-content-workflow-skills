# 写作偏好规则

仅在 `writing-preference-learning` 已触发后读取。目标是保存可追溯的改稿证据，并让候选、正式和停用规则具有清晰生命周期。

## 一、定位与读取

优先使用对话中已经确认的内容项目和文件。没有明确项目时，只在当前工作区内按语义查找可能相关的内容目录，不扫描其他项目或无关素材库。

先确定四个路径变量：

- `{内容项目目录}`：同一选题、平台和内容形式的工作目录。
- `{AI初稿}`：AI 生成且尚未被用户编辑的对照基线。
- `{用户编辑稿}`：用户实际修改或明确认可的版本。
- `{偏好目录}`：已有写作偏好目录；若不存在，标准内容模板优先使用 `00_个人背景/写作偏好/`，其他项目使用当前工作区内语义清楚的 `写作偏好/`。

数字前缀和具体文件名只是兼容示例，不是使用本 Skill 的前提。

按顺序读取当前项目中实际存在且与本篇相关的文件：

1. `00_读取回执.md`
2. `01_正文素材包.md`
3. `02_口喷原稿.md`，仅当需要判断用户是否明确说明修改原因时
4. `03_正文执行单.md`
5. `04_主张与证据.md`
6. `{AI初稿}`，常见命名包括 `06_AI初稿_*`、`*AI草稿*`
7. `{用户编辑稿}`，常见命名包括 `08_本人编辑稿_*`、`08_本人修改稿_*`、`*用户修改稿*`
8. `{偏好目录}`中的当前、候选、停用写作偏好文件
9. 当前平台的真实格式或内容限制，仅在项目内已有或用户提供时读取

同时确认选题、目标用户、内容形式、两个稿件是否同源、用户是否修改或确认过编辑稿，以及是否存在多个版本。

文件名、内容形式或版本无法配对时，不根据最新修改时间擅自猜测；列出路径和修改时间，让用户选择。

## 二、保护原稿和历史

- `{AI初稿}`是不可变对照基线。
- `{用户编辑稿}`是用户工作稿，不在学习过程中修改。
- 中央改稿证据使用 `YYYYMMDD_主题关键词_内容形式.md`。同名证据已存在且代表不同版本时，使用 `_v2`、`_v3` 递增，不覆盖旧文件。
- 同一证据需要补充时，保留原有内容并新增带日期的补充小节。
- `{内容项目目录}`中已有的改稿差异报告保留既有历史；没有固定命名要求，标准模板可使用 `09_改稿差异报告.md`。重新分析时更新摘要并追加本次分析记录，不静默删除旧结论。

## 三、差异对齐

按以下层级对齐：

1. 标题、封面或首图文字
2. 开头
3. 正文段落和小标题
4. 案例、数据和来源
5. 方法和步骤
6. 结尾与 CTA
7. 格式、断句和排版

每项有意义的修改记录：位置、前后必要片段、增加／删除／替换／移动／重组、是否改变事实、是否改变观点、结构和节奏、平台范围、原因证据等级。

错别字、标点、无意义空格、文件格式修复、不影响表达的细小同义词替换，以及名称、时间、价格和数字的单纯校正，只合并统计，不生成候选规则。

## 四、主要分类

每项修改只能选择一个主要分类；必要时补充一个次要分类。

### 1. 事实修正

包括名称、时间、价格、版本、数据、来源和案例归属修正，删除未经验证的效果或承诺。

- 不进入写作偏好。
- 在证据中标记事实后续及其应回到的来源。
- 除非用户同时明确要求，否则不在偏好学习任务中静默修改事实源或正文。
- 同类事实错误反复出现时，记录为正文生成检查项，而不是文风规则。

### 2. 当前任务特例

包括只因本篇不适合而删段、敏感案例不公开、本次不转化，以及本次特殊长度或交付要求。

- 只留在当前证据中，不进入长期候选。

### 3. 平台适配

包括视频口播短句、小红书首屏和拆段、图片逐页重组、公众号完整论证，以及平台标题、封面、字数、排版和 CTA 限制。

- 可以成为候选，但必须写明平台和内容形式，不能外推到全部内容。

### 4. 结构调整

包括结论前置、删除长背景、改变论证顺序、先案例后方法、增加边界、合并或拆分段落。

- 第一次出现标记为单次观察；跨选题再次出现时更新原候选证据。

### 5. 稳定表达偏好

包括人称和称呼、句长与停顿、口头表达、直接程度、反感的 AI 套话、标题、开头、案例、结尾和 CTA 的稳定选择。

- 用户明确说是长期规则时标记待用户确认；从一次差异推测时只做单次观察。
- 不猜测人格、情绪或完整风格。

### 6. 观点与立场修正

包括删除 AI 擅加判断、改写核心结论、补充适用边界，以及拒绝某种营销或价值判断。

- 具体观点应回到用户观点或内容事实源，不写成文风。
- “AI 不得替用户决定观点”属于生成边界，不需要复制为大量具体偏好。

### 7. 商业承接调整

包括删除硬卖、改为自然结束、更换资料／私信／社群／产品入口，以及调整产品位置和转化强度。

- 真实产品、资料和 CTA 事实不作为文风。
- 多次稳定出现的转化节奏可以成为限定平台和内容类型的候选。

## 五、修改原因的证据等级

每项原因只使用以下等级：

- `用户明确说明`：用户直接解释过。
- `规则直接判断`：例如删除虚假数据，明显属于事实修正。
- `推测待确认`：差异支持一个假设，但不能称为用户偏好。
- `无法判断`：只保留差异，不生成规则。

不能因为一次删减就写“用户不喜欢长文”。可以写“本篇删除两段背景；原因未明确，不外推”。

## 六、改稿证据和项目报告

中央证据保存到：

`{偏好目录}/改稿证据/YYYYMMDD_主题关键词_内容形式.md`

至少包含：

```markdown
# 改稿证据：{主题关键词}

- 分析日期：
- 内容形式：
- AI 初稿：
- 用户编辑稿：
- 当前选题：
- 目标用户：
- 用户是否说明修改原因：

## 修改 M001｜{名称}

- 修改位置：
- AI 原写法：
- 用户修改后：
- 修改动作：增加／删除／替换／移动／重组
- 主要分类：
- 次要分类：无／具体类别
- 是否改变事实：
- 是否改变观点：
- 修改原因：
- 原因证据等级：
- 适用范围：仅本篇／具体平台／具体内容类型／可能跨内容
- 是否形成候选偏好：是／否
- 对应候选编号：无／P001
```

结尾统计七种主要分类和“无法判断原因”的数量。引用必要片段即可，不复制整篇正文。

当前项目的改稿差异报告只保存便于创作人员查看的摘要：源文件、有效修改数、分类统计、候选摘要、未入候选的重要变化、冲突、待确认和中央证据路径。

## 七、候选写作偏好

候选统一写入 `{偏好目录}/候选写作偏好.md`，使用稳定 `P001`、`P002` 编号。

```markdown
## P001｜{候选名称}

- 候选规则：
- 适用平台：
- 适用内容类型：
- 不适用场景：
- 当前状态：单次观察／重复出现／待用户确认／已升级
- 证据次数：
- 首次发现日期：
- 最近证据日期：
- 来源证据：
  - {改稿证据文件与修改编号}
- 反例或冲突：
- 修改原因是否明确：
- 建议执行方式：
- 机械套用风险：
- 待确认问题：
- 升级为：无／R001
```

更新规则：

- 已有候选使用等价旧字段时，按语义继续维护；只在实际更新该条时补齐必要字段，不机械重写全部历史记录。
- 相同或近义候选再次出现时更新原编号、证据次数和来源，不新建重复规则。
- 新证据范围不同则拆分或收窄，不能强行扩大。
- 发现反例时记录反例，不静默删除。
- 与当前规则冲突时列出冲突，等待用户判断。
- 与停用规则相近时不自动恢复。

## 八、候选升级和回归测试

单次改稿永不自动升级。候选可进入“待用户确认”的条件包括：

- 用户明确说以后都这样写，或说明它是长期规则；
- 同一修改在至少三篇不同选题中出现；
- 在另一段未参与提炼的真实内容上完成回归测试。

满足条件也不能自动写入当前偏好。只有用户明确确认候选编号或规则范围后才能升级。

升级前选择一段未参与提炼的真实内容：保留事实、观点和任务目标，只应用一条待测规则，对比应用前后，检查事实改变、必要信息丢失、机械结构、平台适配和反例。测试结果补入候选记录。失败时收窄规则或补充不适用场景，并向用户说明。

## 九、当前写作偏好

`{偏好目录}/当前写作偏好.md` 开头必须说明：

```markdown
# 当前写作偏好

> 本文件只包含用户已经确认的执行规则。正文生成时按平台和内容类型读取适用规则。候选偏好不在这里执行。
```

正式规则使用稳定 `R001`、`R002` 编号：

```markdown
## R001｜{规则名称}

- 执行规则：
- 适用平台：
- 适用内容类型：
- 不适用场景：
- 正面示例：
- 反面示例：
- 机械套用风险：
- 确认方式：用户明确确认
- 确认日期：
- 来源候选：P001
- 支持证据：
- 反例和边界：
- 当前状态：启用
```

规则必须是可执行动作，不能只是“更有人味”“开头要吸引人”。升级后保留候选历史并标记其正式编号。

## 十、停用与冲突

用户明确停用正式规则时：

- 在当前文件把该规则状态改为停用，不删除正文。
- 在 `{偏好目录}/停用写作偏好.md` 记录原正式编号、原规则、停用原因、停用日期、用户原始指令和替代规则。
- 正文生成不得继续执行停用规则。

发生冲突时，同时列出双方规则和证据。先判断能否通过平台、内容类型或场景范围拆分；不能解决时等待用户选择，不以“更新”为名覆盖旧规则。

## 十一、正文生成的读取边界

正文生成只执行 `当前写作偏好.md` 中适用且启用的规则。候选文件只用于发现潜在冲突，不直接执行。

顺序为：本次用户明确要求 → 事实与用户观点 → 平台硬限制和产品边界 → 匹配的正式写作偏好。

## 十二、最终汇报

学习完成后简洁汇报：

- AI 初稿和用户编辑稿；
- 内容形式和有效修改数；
- 七类修改统计及原因无法判断数；
- 新增或更新的候选及适用范围；
- 未进入候选的重要修改；
- 与当前、停用规则的冲突；
- 建议确认升级的编号和需要用户解释的修改；
- 实际写入文件。

没有明确确认时写明：`本次只更新改稿证据和候选偏好，没有修改当前写作偏好。`
